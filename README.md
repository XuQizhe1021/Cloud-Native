## 开发规范

## Git 提交规范

1. 每次提交只解决一类问题，避免把“新功能、修 Bug、改文档”混在同一个提交里。
2. 提交前先自查：
   - 代码能否正常运行
   - 关键接口是否已联调
   - 文档是否需要同步更新
3. 不提交大体积无关文件、虚拟机文件、临时日志和本地缓存文件。
4. 当前仓库已忽略：
   - `ubuntukelong/`
   - `jenkins.war`
5. 提交信息建议使用统一前缀，便于课程阶段整理记录。

推荐提交类型：

| 前缀 | 用途 | 示例 |
|---|---|---|
| `feat` | 新功能 | `feat: 完成报修工单创建接口` |
| `fix` | 修复问题 | `fix: 修正库存扣减并发校验` |
| `docs` | 文档更新 | `docs: 补充 Kubernetes 部署说明` |
| `refactor` | 重构 | `refactor: 拆分网关鉴权过滤器` |
| `chore` | 杂项维护 | `chore: 调整项目目录结构` |

## 代码要求

### 通用要求

1. 代码必须服务于真实业务，禁止出现无意义占位文案、无用途接口、无用途类。
2. 命名要清晰，变量名、方法名、接口名必须体现业务语义。
3. 默认添加必要的中文注释，尤其是：
   - 复杂业务流程
   - Feign 调用逻辑
   - 熔断降级逻辑
   - Kubernetes 部署关键配置
4. 发现设计变更时，要同步更新相关文档，至少包括 `README.md` 和对应 `docs/` 文档。
5. 代码提交前，尽量保证删除无用代码、无用依赖和废弃配置。

### 后端要求

1. 后端统一使用 Spring Boot + Spring Cloud 体系。
2. 微服务职责必须清晰，禁止把多个业务强行塞进同一个服务。
3. 必须保留并能演示以下能力：
   - 服务注册与发现
   - Feign 服务调用
   - 基于 LoadBalancer 的负载均衡
   - 熔断降级
   - API Gateway 统一认证与路由
4. 接口返回结构尽量统一，便于前端联调。
5. 配置文件按环境区分，避免把开发环境地址写死在业务代码里。

### 前端要求

1. 前端必须作为独立项目启动，不能只是双击 HTML 在浏览器中打开。
2. 页面风格保持简洁、现代化，优先采用侧栏、顶部栏、抽屉等布局。
3. 页面文案必须贴合“校园报修与备件管理平台”业务，不使用空洞占位内容。
4. 接口调用统一封装，避免在页面中到处直接写请求逻辑。
5. 页面至少覆盖：
   - 登录页
   - 工单列表/详情
   - 备件管理
   - 用户管理

### 部署与脚本要求

1. Kubernetes 相关资源统一使用 YAML 管理。
2. 自动化操作优先写成 Bash 脚本，避免每次手动重复输入命令。
3. 服务部署时应保证配置、镜像、服务名与文档保持一致。
4. Prometheus、Jenkins、Gateway、Eureka 和 3 个核心微服务都应有清晰的部署说明。

## 目录与文件约定

1. `docs/`：存放企划书、架构文档、教学文档等说明材料。
2. `backend/`：存放各 Spring Cloud 微服务。
3. `frontend/`：存放前端独立项目。
4. `deploy/`：存放 Kubernetes YAML、ConfigMap、Secret 等部署文件。
5. `scripts/`：存放 Bash 自动化脚本。

## 联调与交付约定

1. 开发阶段采用“Windows 编码，VMware 虚拟机部署”的模式。
2. 本机先完成单服务开发与联调，再进入容器化和 K8s 部署。
3. 每完成一个里程碑，应至少检查：
   - 功能是否可演示
   - 文档是否同步
   - YAML 是否可复用
   - 提交记录是否清晰
4. 课程答辩前，应保证最少可完整演示：
   - 用户登录
   - 创建报修工单
   - 工单处理
   - 备件扣减
   - 网关转发
   - Feign 调用、负载均衡、熔断
   - Prometheus 监控页面
   - Kubernetes 集群节点与 Pod 状态
