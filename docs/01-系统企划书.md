# 校园报修与备件管理平台系统企划书

## 1. 项目概述

### 1.1 项目名称
校园报修与备件管理平台

### 1.2 项目定位
本系统面向校园场景，解决“学生或老师提交报修申请后，后勤人员无法高效分派、维修记录不透明、维修备件库存难以联动”的问题。系统以云原生方式实现，既满足课程对微服务、Kubernetes、CI/CD、监控的要求，又具有真实业务意义，适合作为课程实践项目。

### 1.3 项目目标
1. 完成一个真实可演示的多微服务系统，而不是简单的增删改查拼接项目。
2. 至少落地 3 个完整后端微服务，满足课程要求。
3. 实现基于 Spring Cloud 的服务注册发现、Feign 调用、负载均衡、熔断降级。
4. 通过 API Gateway 实现统一认证与路由。
5. 在 Kubernetes 集群中完成部署，并接入 Jenkins、Prometheus。
6. 采用 Maven 聚合父工程管理多个子模块，方便统一依赖、版本和打包配置。

## 2. 立项原因

校园内最常见的后勤问题之一就是设备报修，例如宿舍空调故障、教室投影损坏、实验室门禁异常。传统流程通常依赖微信群、纸质登记或口头转达，存在以下痛点：

1. 报修入口分散，无法统一追踪。
2. 用户不知道工单处理到哪一步。
3. 维修人员无法快速查询报修人信息。
4. 维修过程中会消耗灯泡、电源模块、插座面板等备件，但库存与工单脱节。
5. 管理员难以统计维修效率、备件消耗量和系统运行情况。

因此，本项目选择“报修 + 备件管理”作为业务主题，功能真实，结构清晰，也天然适合拆分为多个微服务。

## 3. 用户角色

1. 学生/教师用户
   - 提交报修申请
   - 查看个人工单状态
   - 查看维修结果

2. 维修人员
   - 查看待处理工单
   - 接单、处理、完工
   - 记录维修备注与备件使用情况

3. 管理员
   - 管理用户信息
   - 管理备件库存
   - 查看工单统计与服务状态

## 4. 系统范围

### 4.1 本次课程实践必须完成的范围

#### 微服务 1：用户管理服务 `user-service`
负责系统用户的基础信息管理，满足课程要求中的“1 个用户管理相关微服务”。

核心能力：
1. 用户注册/录入
2. 用户登录
3. 用户角色管理（普通用户、维修人员、管理员）
4. 根据用户 ID 查询用户资料
5. 向其他服务提供用户信息查询接口

#### 微服务 2：报修工单服务 `repair-service`
负责核心业务工单流转，是系统的主业务服务之一。

核心能力：
1. 创建报修工单
2. 查询工单详情
3. 工单接单
4. 工单状态流转（待处理、处理中、已完成、已关闭）
5. 记录维修备注
6. 通过 Feign 调用用户服务，补充报修人/维修人员信息
7. 通过 Feign 调用库存服务，执行备件扣减或校验

#### 微服务 3：备件库存服务 `inventory-service`
负责维修备件的库存管理，是系统的第二个业务服务。

核心能力：
1. 备件列表维护
2. 库存新增与修改
3. 备件库存查询
4. 对接报修服务进行库存占用/扣减
5. 低库存预警字段支持

### 4.2 支撑性组件

以下组件不计入“3 个业务微服务”数量，但为系统必须组成部分：

1. 注册中心：`eureka-server`
2. API 网关：`gateway-service`
3. 前端应用：`repair-web`
4. Jenkins：自动化构建与部署
5. Prometheus：系统监控
6. Kubernetes Dashboard：集群可视化管理
7. Argo CD：GitOps 持续部署

### 4.3 课程实践要求补充对齐

结合老师 PDF 中的三次实践内容，本项目在实现边界上再补充以下约束：

1. 工程结构采用 `1 个 Maven 父工程 + 多个子模块` 的聚合方式组织。
2. `eureka-server`、`gateway-service`、`user-service`、`repair-service`、`inventory-service` 都作为独立子模块管理。
3. 每个业务微服务都要落实到自己的数据库 schema 与核心数据表，不能只停留在接口层。
4. 网关不仅负责路由，还要明确体现访问权限验证能力。
5. 熔断不仅要实现，还要准备可演示、可验证的故障触发场景。

## 6. 微服务拆分合理性

### 6.1 为什么这样拆
1. `user-service` 独立后，所有业务服务都可以通过统一接口获取用户信息，避免重复开发。
2. `repair-service` 承载主业务流程，适合作为 Feign 调用发起方。
3. `inventory-service` 具备独立业务价值，且与报修场景强相关，适合作为第二个业务服务。
4. 网关、注册中心、监控、CI/CD 作为基础设施，与业务服务职责清晰分离。

### 6.2 如何体现课程要求
1. Feign 服务调用：`repair-service` 调用 `user-service` 与 `inventory-service`
2. Feign 负载均衡：部署多个 `inventory-service` 副本，通过 Spring Cloud LoadBalancer 转发
3. Feign 熔断：库存服务异常时，报修服务返回“暂时无法扣减库存，请稍后重试”的降级信息
4. 服务注册发现：所有微服务启动后注册到 `eureka-server`
5. API 网关认证与路由：统一从 `gateway-service` 进入

## 7. 关键业务流程

### 7.1 用户提交报修
1. 用户登录前端
2. 网关校验身份
3. 前端调用报修服务创建工单
4. 报修服务保存工单并通过 Feign 查询用户服务，补全报修人信息
5. 返回工单创建成功结果

### 7.2 维修完工并扣减备件
1. 维修人员打开工单详情
2. 填写维修结果并选择使用的备件
3. 报修服务通过 Feign 调用库存服务执行库存扣减
4. 若库存服务正常，则更新工单为“已完成”
5. 若库存服务异常，则触发熔断降级，提示稍后重试，并保留工单在“处理中”

## 8. 前端设计要求

前端不作为微服务数量统计对象，但必须独立运行，不能只是双击 HTML 在浏览器中打开。

建议方案：
1. 技术栈：Vue 3 + Vite + Element Plus
2. 运行方式：开发阶段使用 `npm run dev` 独立启动；部署阶段打包为静态资源容器
3. 风格：现代化、简洁、偏后台管理系统
4. 布局：左侧侧栏 + 顶部导航，移动端或窄屏使用抽屉式菜单

建议页面：
1. 登录页
2. 工单列表页
3. 工单详情页
4. 备件管理页
5. 用户管理页
6. 系统监控入口页
