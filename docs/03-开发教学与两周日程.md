# 校园报修与备件管理平台开发教学与两周日程

## 1. 先说最重要的结论

这份文档必须严格跟着老师 PDF 的顺序走：

1. **实践一：先做父工程 + `eureka-service` + 数据库创建**
2. **实践二：再做业务微服务 + Feign + 负载均衡 + 数据表**
3. **实践三：最后做 Gateway + 权限验证 + 熔断**

所以请你先把下面 3 句话记住：

1. 第一个要完成的子项目一定是 **`eureka-service`**
2. 没完成实践一，不进入 Feign 联调
3. 没完成实践二，不优先写 `gateway-service`

## 2. 你现在的真实起点

你当前并不是“什么都要一起做”的状态，而是：

1. 你手里有老师给的虚拟机文件
2. 你目前只装了一台虚拟机
3. 你现在最需要的是一条**不会做乱**的推进顺序

这反而是好事，因为现在最适合把主线理顺。

### 2.1 当前最合理的推进策略

现阶段建议这样做：

1. Windows 本机负责写代码、建项目、跑本地服务
2. 现有虚拟机先作为环境熟悉与后续部署准备
3. 三次实践主链路先在本机跑通
4. 等三次实践结束，再扩展到 3 台虚拟机、K8s、Jenkins、Prometheus

也就是说：

**现在先不要被“K8s、网关、Jenkins、Prometheus”带着跑。**

## 3. 老师给的文件到底怎么用

你当前目录里有 3 份关键内容：

1. `E:\trae\云原生\ubuntukelong`
   - 这是已经配置过一部分基础环境的 Ubuntu 虚拟机文件夹
   - 里面的 `.vmx` 是 VMware 的配置文件
   - 里面的 `.vmdk` 是虚拟机硬盘文件

2. `E:\trae\云原生\本虚拟机文件说明.pdf`
   - 用来说明老师预装了什么
   - 通常意味着 `containerd`、`k8s` 相关镜像、基础工具已经准备了一部分

3. `E:\trae\云原生\jenkins.war`
   - 这是后续扩展阶段才用到的 Jenkins 安装包
   - 现在不是最优先处理的内容

### 3.1 这三样东西的优先级

当前顺序应该是：

1. 先用 `ubuntukelong` 把环境看明白
2. 再完成实践一、二、三的本地开发主线
3. 最后才用 `jenkins.war` 做课程扩展展示

## 4. 你现在不该先做什么

为了避免偏题，先把几件**现在不该优先做**的事说清楚：

1. 不要一上来先写 `gateway-service`
2. 不要一开始就把全部微服务都建出来
3. 不要还没完成 `eureka-service` 就去写 Feign 联调
4. 不要还没完成实践三就花大量时间折腾熔断演示
5. 不要还没跑通三次实践主线就把主要精力放在 K8s、Jenkins、Prometheus 上

## 5. 开始前准备

## 5.1 Windows 本机先准备的软件

请先确认 Windows 上有这些软件：

1. JDK 17
2. Maven 3.9+
3. IntelliJ IDEA
4. VS Code
5. MySQL 8
6. Git
7. Node.js 20 LTS
8. VMware Workstation

### 5.1.1 为什么现在就要装 MySQL

因为老师 PDF 在实践一里就要求：

1. 安装 MySQL
2. 完成数据库创建
3. 设计微服务用的数据库

所以 MySQL 不是实践二才装，而是实践一就要准备。

## 5.2 先把虚拟机导入 VMware

### 操作步骤

1. 打开 `VMware Workstation`
2. 点击 `File`
3. 点击 `Open...`
4. 进入 `E:\trae\云原生\ubuntukelong`
5. 选择 `.vmx` 文件
6. 点击打开

如果弹出：
`Did you move or copy this virtual machine?`

请选择：
`I copied it`

### 5.2.1 现在只装了一台虚拟机够不够

**够。**

对当前阶段来说：

1. 实践一不要求你先把 3 台虚拟机全部整好
2. 实践二的核心也还是微服务本地联调
3. 3 台虚拟机更偏向后续 Kubernetes 扩展阶段

所以你现在完全可以先只保留 1 台虚拟机，把精力用在实践主线上。

## 6. 实践一：先完成底座

## 6.1 实践一的目标

实践一结束时，你应该得到这些结果：

1. 确定项目题目与要开发的微服务
2. 建好 Maven 父工程
3. 建好并跑通 `eureka-service`
4. 安装好 MySQL
5. 完成数据库设计

注意，这时候你**还不需要**把业务链路全部打通。

## 6.2 实践一先做哪个子项目

答案只有一个：

**先做 `eureka-service`。**

这是老师 PDF 里明确写出来的：

1. 完成父项目的创建
2. 完成子项目 `eureka-service`

所以如果现在要开始写代码，顺序必须是：

1. 先建父工程
2. 再建 `eureka-service`
3. 先把 `eureka-service` 启动成功

## 6.3 实践一步骤 1：确定微服务题目

你现在的题目已经定为：

`校园报修与备件管理平台`

后续对应的核心微服务可以先定为：

1. `user-service`
2. `inventory-service`
3. `repair-service`

这里先确定名字即可，不用现在全部创建。

## 6.4 实践一步骤 2：创建父工程

### 推荐目录

```text
E:\trae\云原生\backend-parent
```

### 这个父工程要做到什么

1. 统一管理依赖版本
2. 统一管理插件版本
3. 统一管理子模块

### 父工程关键要求

1. `packaging` 必须为 `pom`
2. 要能通过 `<modules>` 管理子项目
3. 后续所有微服务都挂到这个父工程下面

### 现在先不要做什么

现在不要在父工程里一口气先把 `gateway-service`、`repair-service` 全部写起来。

实践一阶段只要求你把骨架立住。

## 6.5 实践一步骤 3：创建 `eureka-service`

### 为什么它一定是第一个

因为老师 PDF 直接写了：

1. 完成子项目 `eureka-service`
2. 掌握 Eureka 服务注册原理

这说明它不是“众多模块中的一个”，而是**第一阶段的核心成果**。

### 这一阶段你只需要让它完成什么

1. 工程创建完成
2. 依赖配置完成
3. 能作为注册中心启动
4. 能访问管理页面或能看到注册中心启动成功日志

### 这里先不要纠结的点

1. 先不要把业务服务一起注册进来
2. 先不要把网关接进来
3. 先不要引入熔断逻辑

## 6.6 实践一步骤 4：安装 MySQL 并创建设计用数据库

老师 PDF 明确要求：

1. 安装 MySQL（推荐 8.0.26）
2. 设计微服务用的数据库

### 推荐先建 3 个业务库

1. `user_db`
2. `repair_db`
3. `inventory_db`

### 为什么实践一就建库

因为实践一的目标之一就是先把“后面要用什么数据库结构”想清楚。

这时你可以先：

1. 把库建出来
2. 把表结构草图画出来
3. 不急着把全部业务接口都写完

## 6.7 实践一完成检查清单

做到下面这些，实践一才算真的结束：

1. 父工程已经创建
2. `eureka-service` 已经创建并能启动
3. MySQL 已安装
4. 3 个业务库已经规划完成
5. 你能说清楚什么是服务注册与发现

如果这 5 条没有全满足，就不要进入实践二。

## 7. 实践二：再进入业务微服务联动

## 7.1 实践二的目标

实践二关注的是：

1. Feign 调用
2. 服务提供者与服务使用者
3. 服务注册发现
4. 负载均衡
5. 每个微服务所用的数据库及表

所以实践二的关键词不是“网关”，而是：

**服务之间开始相互调用。**

## 7.2 实践二开始前必须满足什么

只有下面这些都成立，实践二才开始：

1. `eureka-service` 已跑通
2. 父工程已存在
3. MySQL 已安装
4. 你已经知道有哪些业务服务要开发

## 7.3 实践二推荐开发顺序

请严格按下面顺序做：

1. `user-service`
2. `inventory-service`
3. `repair-service`

### 为什么是这个顺序

因为：

1. `user-service` 和 `inventory-service` 更适合先当服务提供者
2. `repair-service` 需要调用它们，所以更适合后做
3. 这样最符合“先提供、后消费”的逻辑

## 7.4 实践二步骤 1：创建 `user-service`

### 这个服务这一阶段至少要做什么

1. 用户新增
2. 用户查询
3. 登录
4. 用户列表

### 同时要落地什么数据表

至少创建：

1. `users`

### 实践二里它还必须做什么

1. 启动后注册到 `eureka-service`
2. 能被其他服务通过服务名找到

## 7.5 实践二步骤 2：创建 `inventory-service`

### 这个服务这一阶段至少要做什么

1. 备件新增
2. 备件查询
3. 库存修改
4. 库存扣减

### 同时要落地什么数据表

至少创建：

1. `parts`

### 实践二里它还必须做什么

1. 启动后注册到 `eureka-service`
2. 后续为 `repair-service` 提供远程调用能力

## 7.6 实践二步骤 3：创建 `repair-service`

这是实践二里真正的“服务使用者”。

### 这个服务这一阶段至少要做什么

1. 创建工单
2. 工单列表
3. 工单详情
4. 接单
5. 完工

### 同时要落地什么数据表

至少创建：

1. `repair_order`
2. `repair_part_usage`

### 它为什么最后做

因为它要通过 Feign 去调用：

1. `user-service`
2. `inventory-service`

如果前两个服务没准备好，`repair-service` 很容易写乱。

## 7.7 实践二步骤 4：完成 Feign 调用

在 `repair-service` 中至少完成两条调用：

1. 调用 `user-service` 获取报修人/维修人信息
2. 调用 `inventory-service` 查询或扣减库存

### 这一阶段最重要的验证点

你要确认：

1. 不是写死 URL
2. 是通过服务名调用
3. 调用链真的经过 Eureka 注册发现

## 7.8 实践二步骤 5：完成负载均衡

老师 PDF 明确要求完成基于 Feign 的负载均衡。

### 最简单的演示方法

让 `inventory-service` 跑两个实例。

例如：

1. 第一个实例端口 `8083`
2. 第二个实例端口 `8084`
3. 服务名都注册为 `inventory-service`

然后让 `repair-service` 通过服务名调用它。

### 你要观察什么

1. 两个实例都注册到了 Eureka
2. 调用不会固定打到同一个端口
3. 能向老师解释“这是通过服务名 + 负载均衡实现的”

## 7.9 实践二完成检查清单

做到下面这些，实践二才算完成：

1. `user-service` 已完成并注册
2. `inventory-service` 已完成并注册
3. `repair-service` 已完成并注册
4. `repair-service` 已能通过 Feign 调用其他服务
5. `inventory-service` 已能演示多实例负载均衡
6. 每个微服务所需数据库表已真正创建

只要这 6 条还有缺口，就不要急着进入实践三。

## 8. 实践三：最后做网关、权限和熔断

## 8.1 实践三的目标

实践三才开始处理：

1. Gateway API 网关
2. 访问权限验证
3. 熔断机制
4. 熔断有效性验证

也就是说，这一阶段处理的是：

**统一入口 + 安全控制 + 下游异常处理**

## 8.2 实践三开始前要确认什么

开始实践三前，请先问自己 4 个问题：

1. `repair-service` 是否已经能调用 `user-service`？
2. `repair-service` 是否已经能调用 `inventory-service`？
3. Feign 负载均衡是否已经演示成功？
4. 业务数据库与表是否已经齐了？

只要有一个回答是“没有”，就先回去补实践二。

## 8.3 实践三步骤 1：创建 `gateway-service`

这是实践三里才应该出现的子项目。

### 这一阶段它至少要做什么

1. 成为统一入口
2. 按路径转发请求
3. 放行登录接口
4. 拦截未登录访问

### 推荐路由

1. `/api/users/**` -> `user-service`
2. `/api/inventory/**` -> `inventory-service`
3. `/api/repairs/**` -> `repair-service`

### 这里为什么不该提前做

因为在实践一、实践二时，你更需要先把：

1. 注册中心做稳
2. 业务服务做稳
3. Feign 调用做稳

否则网关只会把问题包起来，不会让主链路更清楚。

## 8.4 实践三步骤 2：实现访问权限验证

老师 PDF 里明确点了“访问权限验证的实现”。

### 推荐最小实现

1. 登录成功后生成 Token
2. 网关校验 Token
3. 未登录只能访问登录接口
4. 已登录才能访问受保护接口

### 最低演示要求

至少演示这两种情况：

1. 不带 Token 访问 `/api/repairs/**` 被拦截
2. 带 Token 再访问同一路径，能够成功通过

## 8.5 实践三步骤 3：实现熔断

老师 PDF 里写的是：

1. 实现项目的熔断机制
2. 验证熔断机制的有效性

### 最推荐的熔断位置

放在：

`repair-service -> inventory-service`

### 为什么选这里

因为：

1. 这是明确的 Feign 调用链
2. 容易模拟异常
3. 业务意义直观

### 推荐降级效果

当库存服务异常时：

1. 工单服务不直接崩溃
2. 返回“库存服务暂时不可用，请稍后重试”
3. 工单状态保持在可继续处理的中间状态

## 8.6 实践三步骤 4：验证熔断有效性

这一条很多人会漏掉，但老师 PDF 是明确要求的。

### 演示方法

你可以这样做：

1. 正常启动所有服务
2. 让 `repair-service` 调用 `inventory-service`
3. 然后手动停掉一个库存服务实例，或者人为制造超时
4. 再次调用相关接口
5. 观察系统是否返回降级结果而不是直接报错崩掉

### 你要向老师说明什么

1. 熔断的作用不是“让错误消失”
2. 熔断的作用是“在下游异常时保护系统主流程”

## 8.7 实践三完成检查清单

做到下面这些，实践三才算完成：

1. `gateway-service` 已建成统一入口
2. 路由转发已生效
3. 权限验证已生效
4. 熔断逻辑已生效
5. 熔断效果已被实际验证过
